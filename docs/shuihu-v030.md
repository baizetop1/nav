# 白泽水浒 0.30.0 · 招贤保障与有限补给

普通招贤仍为五星 1%、四星 6%、三星 23%、二星 45%、一星 25%；原有 20 / 50 / 100 次星级保底、专属目标 25% 和连续四次未得目标后第五次必中均不变。十连继续逐次执行普通招贤，使用原有随机数序列，不重抽、不改变结果星级。

## 迎贤荐书

连续十次普通招贤没有新好汉入寨，额外获得一封迎贤荐书。单抽与十连共同累计；普通招贤抽到新人时清零。每发一封荐书后从零重新累计，荐书可以保存。专属招贤不增加或清空这项普通招贤进度。

荐书可在招贤页自选一位尚未入寨的一至三星正册好汉，不要求提前相识。选择并确认后必定入寨；不随机分配人物，不包含四星、五星或外传人物。全部低星正册已经入寨后，一封荐书可折换 10 点荐贤积分。

原抽取所得的线索、信物与功勋照常保留，荐书属于额外保障。原来的星级保底不会因为使用荐书、积分迎贤而重置；兑换也不计入招贤抽取次数。

## 荐贤积分

每次普通或专属招贤只得到传闻线索或重复好汉，额外获得 1 分；抽到新入寨好汉不加分。积分不会过期，可确定邀请已相识、尚未入寨的正册好汉。

| 人物星级 | 所需积分 |
| --- | ---: |
| 一星 | 10 |
| 二星 | 15 |
| 三星 | 25 |
| 四星 | 40 |
| 五星 | 60 |

名册中既有的“直接迎贤”继续可用：达到对应聚义厅、寨务经营及出征次数要求，再支付碎银即可迎入，不需要抽取。招贤页现在也提示这个入口。

## 招贤令来源

- 每周访贤差事：寨务经营 3 次、战斗胜利 5 次，领取招贤令 2 张；每周一北京时间 00:00 换周。胜利扫荡计入真实胜利次数，失败与撤退不算。
- 六卷各完成一次，分别领取招贤令 2 张。
- 普通副本列表中的每个副本首次通关，领取招贤令 1 张；不把每日材料本和周本每次战斗当作新首通。
- 旧存档已经完成的章节和副本可以补领这批新增一次性奖励。
- 原每日寨中悬赏、每日限购三张、十碎片合成一张等渠道保持原样。招贤页提供领取条件、采买、合成与寨中悬赏跳转。

周常和连续无新人进度从更新后的实际操作开始记录。历史抽取只保留原有星级保底和专属缘分，不凭总抽数推算或补发荐书、积分。

## 界面和存档

招贤页显示原星级保底剩余次数、连续无新人进度、荐书和积分。单抽及十连结果弹窗顶部显示额外保障所得；迎贤和补给领取都有收获弹窗。补给清单折叠显示，避免大量首通条目挤占招募区域。

新增可选状态 `recruit.support`，包含保障计数、库存、领奖记录和周常进度。旧存档可以直接读取，不会自动伪造历史进度；新状态通过明确的存档白名单保存。本机、导出导入和云存档均校验这些字段。

本轮需更新 Worker，使其提供 `recruitSupport: 1` 能力。新前端遇到旧 Worker 会阻止上传，并保留本机进度；新 Worker 会拒绝缺少保障字段的旧页面覆盖已有新进度。此保护不等于服务器托管抽取，游戏仍使用现有可导入存档机制。

**无新数据库表，无 SQL 迁移。** 若更早版本的数据库迁移还未部署，仍按那些版本的说明处理。

## 发布顺序（Git Bash）

先在原项目目录更新 Worker：

```bash
cd /f/nav-main/nav-main
npx wrangler deploy --config cloud/shuihu/wrangler.json
```

成功后再提交并推送前端与对应源代码，每条命令成功后再执行下一条：

```bash
git add -A
git commit -m "新增招贤保障与有限补给 0.30.0"
git pull --rebase origin main
git push origin main
```

如 rebase 出现冲突，先处理冲突再推送。网站更新还需要现有部署流程成功完成。没有自动部署流程时，推送 GitHub 本身不会发布网站。可以在刷新后看到“迎贤保障”和“招贤令从哪里来”确认前端版本。
